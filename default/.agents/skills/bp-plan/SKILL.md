# 需求澄清与规划

局部、明确的小改动可直接进入实现，不强制创建文档。

先检查当前实现与适用规则。明确用户目标、成功条件、范围、兼容约束和风险；只对无法从环境得到且实质影响方案的信息提问。

用户未提供流程时主动组织必要步骤：关键业务未知先集中询问，已有需求直接归纳并推进；用户授权默认原型时说明假设后实现，不把澄清或计划变成重复审批。不要在用途未知时擅自选一种业务来凑交付。

形成能交给实现者执行的计划：目标行为、目录职责、实现方式、接口变化、验证、失败处理和已选默认值。按开发目标读取已安装的对应 UI 或后端专项技能，不能把工作台说明页当作已安装指令。

复杂或多里程碑任务按需使用 `.codex-bp/templates/goal-record.md` 与 `.codex-bp/templates/task-plan.md`，保存到 `goals/<里程碑标识>.md` 与 `plans/<同一标识>.md`，互相链接。已有目标／计划继续复用，用户指定位置优先。小任务无需生成这些文件。

需求至少能回答服务谁、解决什么问题、范围是什么、如何验收。涉及架构时说明模块职责、数据与接口、兼容影响及关键取舍；沿用现有项目结构，不预设所有项目都需要数据库、分层目录或部署流水线。

长任务按里程碑拆成可独立验收的小任务，逐项记录范围、依赖、交付物和验证方式。仅在确有并行收益且已获授权时考虑分工，先约定接口、文件归属与集成责任。已有 PLANS.md 或任务记录时持续更新，不另建冲突的状态来源。

记录重大决策及其原因，避免把待决问题伪装成确定方案。仅在范围或关键方案需要用户决策时确认；已有明确授权后持续推进。
